# 0007 — Windows-first, но не Windows-only: платформенное живёт за узкими швами

**Date:** 2026-07-29

## Context

Цель релиза — Microsoft Store (§11), поэтому единственная платформа, которую мы собираем,
тестируем и публикуем, — Windows. Это не спорный вопрос и не меняется этим решением.

Спорным оказалось другое: **где физически лежит платформенный код.** До сих пор правило
существовало только в головах, и результат уже разъехался. Инвентаризация на 2026-07-29
(`grep -rn "IFDEF WINDOWS" gui/ src/`) даёт три места и три разных ответа:

| место | что делает | как оформлено |
|---|---|---|
| `gui/SpxSettings.pas` | путь к файлу настроек через `GetWindowsSpecialDir(CSIDL_LOCAL_APPDATA)` | за `{$IFDEF}`, с честным не-Windows фолбэком `GetAppConfigDir` — **шов есть** |
| `gui/SpxUi.pas` | `SpxFontCanDraw` / `SpxFontInstalled` поверх `GetGlyphIndicesW` + `GetTextFaceW` | за `{$IFDEF}`, вызывающий видит только предикат — **шов есть** |
| `gui/SpxMainForm.pas` | `SendMessage(…, CB_SETDROPPEDWIDTH, …)` в `SizeLocaleList` | голый Win32 **прямо в форме** — шва нет |

Третья строка появилась 2026-07-29, за час до этого решения, и она показательна: шов не
проламывают намеренно — его просто не заводят, когда нужна одна строчка. Одна строчка,
другая, и через полгода «поддержать вторую платформу» означает читать всю GUI-папку.

Отдельно: слои ниже GUI платформенного кода **не содержат вовсе** — движок (`unit Spintax`)
и editor-core (`SpxStudio.pas`) чисты по построению (§5), а `SpxEditorFont.pas` намеренно
не тянет ни LCL, ни Windows, чтобы консольная сюита могла гонять выбор шрифта с подставным
зондом. Проблема ограничена слоем GUI, и решается тоже в нём.

## Decision

**Windows-first, но не Windows-only.** Всё, что зависит от платформы, прячется за узкой
функцией с осмысленным именем; вызывающий код о платформе не знает.

Правило в трёх пунктах:

1. **`{$IFDEF WINDOWS}` допустим только внутри функции-шва**, не в теле экранной логики.
   Форма, панель, обработчик события не содержат ни `Windows` в `uses`, ни оконных
   сообщений, ни хендлов.
2. **У шва есть не-Windows ветка** — пусть беднее, но осмысленная и документированная.
   «Не компилируется» не считается фолбэком; «отвечает консервативно» считается.
3. **Имя шва описывает вопрос, а не механизм.** `SpxFontCanDraw` — вопрос; `SpxGlyphIndices` —
   механизм, который завтра сменится.

Швы, существующие на дату решения:

```pascal
{ gui/SpxUi.pas — шрифты }
function SpxFontInstalled(const AFamily: string): Boolean;
function SpxFontCanDraw(const AFamily, ASample: string): Boolean;

{ gui/SpxSettings.pas — профиль пользователя }
function SpxPrefsPath: string;
```

**Формы швов отличаются от эскиза в постановке задачи, и намеренно:**

- `SpxFontCanDraw(family, sample)` вместо `SpxFontCoversText(font, text)` — на вход идёт
  **выборка**, а не весь текст. Выборка (`SpxFontSample`, `gui/SpxEditorFont.pas`) — это
  различные символы документа, не более 48; мегабайт прозы даёт ту же выборку, что абзац.
  Замерено: скан мегабайтного кириллического шаблона — 3 мс, и он делается **один раз** на
  рендер, а зонд после этого спрашивают до восьми раз. Передавать в шов весь текст значило бы
  сканировать его восемь раз вместо одного. Имя обязано это отражать, иначе следующий
  вызывающий передаст туда `FEditor.Text`.
- `SpxFontInstalled(family): Boolean` вместо `SpxInstalledMonoFonts: TStringList` — предикат,
  а не список. Список означал бы, что каскад семейств принадлежит адаптеру; каскад — это
  **политика**, он лежит в чистом `SpxEditorFont.pas` (`SPX_EDITOR_FONTS`), покрыт тестами и
  меняется без платформенного кода. Плюс возвращённый `TStringList` — это вопрос владения на
  ровном месте. Оба потребителя (каскад в выборе и список в меню «Вид») спрашивают предикат
  по одному семейству.

## MVP boundary

**R0 собирается, тестируется и публикуется только под Windows.** Linux и macOS:

- **не гейтят** релиз — ни один пункт R0 не ждёт второй платформы;
- **не обещаны** в листинге Store, в README и нигде публично;
- **не тестируются** — CI гоняет консольную сюиту на ubuntu (она чистая и это дешёвая
  страховка от случайного платформенного кода в `src/`), но GUI собирается только на Windows.

То есть швы — это страховка, а не заявка. Их ценность в том, что стоимость второй платформы
остаётся известной, а не выясняется через полгода.

## Consequences

**Что становится дороже.** Одна строчка Win32 больше не пишется на месте: сначала функция,
имя, комментарий и не-Windows ветка. Для `CB_SETDROPPEDWIDTH` это примерно пятнадцать строк
вместо одной.

**Что становится дешевле.** Ответ на вопрос «сколько стоит Linux» читается из списка швов, а
не из всей GUI-папки. И побочно: шов, у которого есть вторая ветка, — это шов, который
**можно подменить в тестах**. Именно это уже даёт `SpxEditorFont`: чистый выбор шрифта
проверяется консольной сюитой с подставным зондом, без окна и без Windows.

**Чего это НЕ означает.** Ни абстрактных фабрик, ни слоя-обёртки над LCL, ни «портируемости»
как отдельной задачи. LCL сам по себе кросс-платформенный; чинить нужно только те места, где
мы обходим LCL и идём в Win32 напрямую. Их сейчас три, и одно из них — долг (см. ниже).

**Долг, заведённый этим решением.** `SizeLocaleList` (`gui/SpxMainForm.pas`) нарушает правило
на момент его записи. Вынести в `SpxUi` за шов вида `SpxSetDropdownWidth(AComboBox, APixels)`
с пустой реализацией вне Windows — задача в `docs/TODO.md`. Записано как долг, а не исправлено
молча: правило, у которого с первого дня есть исключение без записи, перестаёт быть правилом.

## Alternatives considered

- **Ничего не писать, Windows-only честно и до конца.** Отвергнуто не из любви к
  кросс-платформенности, а из-за цены ошибки: правило стоит дёшево *сейчас* и дорого потом.
  Прецедент уже есть — `SizeLocaleList` появился ровно тогда, когда правила не было.
- **Полноценный HAL / интерфейсный слой над платформой.** Отвергнуто как несоразмерное:
  платформенных мест три, а не тридцать, и LCL уже делает эту работу. Абстракция на три
  вызова — это код, который надо читать, ради развязки, которой нет.
- **Взять `SpxInstalledMonoFonts: TStringList` как в эскизе.** Отвергнуто выше по существу:
  утаскивает политику (каскад) в адаптер и заводит владение объектом.

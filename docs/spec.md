# Spintax Studio — спецификация приложения

Нативный Windows-редактор spintax-шаблонов с интерфейсом в духе переводчика
(DeepL): две панели, слева исходный шаблон, справа живой результат. Движок —
готовый `spintax-win` (проходит общий golden-корпус; R0 собирается против `v0.2.0` — там
у диагностики есть позиции и есть `SpExtractDirectives`, см. §4.1/§4.2/§9), встроенный в
процесс. Поверх движка — живой предпросмотр и валидация; **опционально** петля «LLM пишет
→ движок проверяет → LLM чинит» — это уже AI-релиз (R1+), первая Store-подача (R0) идёт
**без AI** (§9).

Рабочее имя — Spintax Studio. Отдельный репозиторий-приложение, потребитель
движка. Движок остаётся чистым и zero-dep; сеть к моделям и GUI живут только
здесь.

---

## 1. Принципы

- **DeepL-метафора.** Минимум хрома, две крупные панели, мгновенный отклик.
  Слева печатаешь/вставляешь/генерируешь шаблон, справа сразу видишь, что из него
  выходит. Управление сверху узкой полосой, детали — в сворачиваемых панелях.
- **Local-first, zero-telemetry.** Приложение — локальный клиент. Ключи моделей и
  настройки лежат у пользователя, никуда не уходят. Движок работает полностью
  офлайн; сеть нужна только для облачных моделей, и её можно не включать вовсе
  (локальная модель или ручное авторство).
- **Один .exe без рантайма.** Нативная сборка, без бандла Node/PHP/Python. Цель
  дистрибуции — **Microsoft Store через MSIX** (обёртка вокруг этого же .exe), детали
  в §11.
- **Офлайн-база — это и стратегия прохождения Store-ревью.** Редактор, валидация, рендер
  и экспорт работают полностью без сети и без ключа модели; AI — опциональная надстройка
  (BYOK или локальная модель). Рецензент Microsoft открывает приложение и проверяет
  всё ключевое, ничего не настраивая, — это резко снижает риск отказа (§11).
- **Hotkey-first.** Любое ключевое действие — с клавиатуры (идея взята со
  spintax.ru). Мышь необязательна.
- **Движок — источник истины.** Предпросмотр и вердикт «валидно/нет» считает
  реальный `spintax-win`, тот же, что стоит в npm/PHP/Python. Не доверяем
  самооценке модели — гоняем через движок.

---

## 2. Идеи, заимствованные со spintax.ru

Явно переносим в Studio (со spintax.ru / app.spintax.ru):

- подсветка вложенных шаблонов и подшаблонов;
- парная подсветка скобок и указание незакрытой;
- **select-and-wrap**: выделил кусок текста, нажал — обернулось в `{...|}`,
  курсор готов дописывать варианты;
- **подбор синонимов** для выделенного слова (у нас — из локального тезауруса
  и/или от LLM, две базы);
- **частичный предпросмотр**: выделил фрагмент шаблона — справа рендерится
  только он, а не весь документ;
- горячие клавиши на все ключевые действия;
- **пакетный экспорт** в Excel/txt/по файлу на текст, с контролем уникальности и
  размера шингла при дедупликации.

Чего на spintax.ru нет и что даёт Studio: нативность и офлайн, движок-как-истина
для валидации, полный superset (перестановки, переменные, условки, плюрали) и
встроенная LLM-петля авторства с проверкой.

## 3. Раскладка главного окна

```
┌───────────────────────────────────────────────────────────────────────┐
│ [locale ▾] [spin: seed|random] [variants: N]      [Generate ▾] [Fix]  │  ← верхняя полоса
├──────────────────────────────────┬────────────────────────────────────┤
│  ШАБЛОН (редактор)               │  РЕЗУЛЬТАТ (предпросмотр)          │
│  подсветка · парные скобки ·      │  один пример рендера              │
│  подчёркивания ошибок             │  [⟳ reroll]  [copy]               │
│                                   │                                    │
│  выделение → wrap / синонимы      │  (частичный предпросмотр при       │
│                                   │   выделении фрагмента слева)       │
│                                   │                                    │
├──────────────────────────────────┴────────────────────────────────────┤
│ Переменные (SpExtract) │ Диагностика (SpValidate) │ Варианты / Экспорт │  ← нижние вкладки
└───────────────────────────────────────────────────────────────────────┘
```

Панели снизу сворачиваются. По умолчанию виден только редактор и результат —
как у DeepL.

## 4. Функциональные модули

### 4.1 Редактор шаблона (левая панель)

- Подсветка синтаксиса: enumerations `{|}`, permutations `[<config>|]`,
  переменные `%var%`, директивы `#set/#def/#include`, условки `{?var?|}`,
  плюрали `{plural n: ...}`, комментарии `/# #/`. Вложенность — разными
  оттенками/глубиной.
- Парные скобки: подсветка пары под курсором; незакрытая/лишняя — из
  `SpValidate` (`bracket.unclosed`, `bracket.mismatched`,
  `bracket.unexpected-closing`).
- Подчёркивания ошибок (squiggles) прямо в тексте по диагностике движка (см. 4.3).
  **Позиции даёт сам движок** (с `spintax-win` v0.2.0): `TSpDiag` несёт
  `Line` / `Column` / `EndLine` / `EndColumn` поверх `Code` / `Severity`. Studio их
  **потребляет напрямую и НЕ переписывает скан валидатора** — это и есть смысл жить
  на движке-как-истине. Контракт потребления:
  - все 1-based; **колонки в code points** от начала строки (одинаково под FPC-UTF-8
    и UTF-16), строки — по редакторному EOL (`\n`, `\r\n`, `\r`). SynEdit тоже считает
    колонку в символах, так что маппинг прямой; если бы движок отдавал байты, Studio
    промахивался бы на каждой кириллической строке — он отдаёт code points, поэтому нет.
  - `Line = 0` означает «позиция неизвестна» (движок локализует editor-critical коды —
    скобки, malformed-директивы, undefined-переменные, unknown-includes, plural arity —
    а редкие оставляет `0/0`, честно, а не наугад). На `Line = 0` squiggle не рисуем:
    диагноз идёт **только в панель** (4.3), без подчёркивания в тексте.
  - `End* > 0` — рисуем подчёркивание на диапазоне `[Line:Column .. EndLine:EndColumn)`;
    `End* = 0` — ставим caret/точечную метку в `Line:Column`.
  Один источник истины — вердикт движка; позиции — вспомогательный слой поверх него и
  никогда не меняют сам вердикт. Squiggles едут в **M2** (вместе с панелью диагностики);
  в M1 их допустимо не иметь. Требование к движку: submodule на теге ≥ `v0.2.0`
  ([ADR 0001](decisions/0001-engine-as-submodule.md) — сейчас пин `v0.1.0`, позиций там ещё нет).
- **Select-and-wrap** (hotkey): выделение → `{выделение|}`; повтор на пустом
  варианте добавляет `|`. Отдельные врапы: в permutation `[...]`, в условку
  `{?VAR?...}`.
- **Синонимы** (hotkey на слове): выпадашка вариантов из тезауруса и/или LLM;
  выбор — вставляет как `{слово|синоним1|синоним2}`.

### 4.2 Живой предпросмотр (правая панель)

- На каждое изменение — `SpRender` одного примера. По умолчанию недетерминирован
  (свежий rng), кнопка **reroll** даёт новый пример.
- **`#include` разворачивает Studio, а не движок.** Движок отдаёт директиву в вывод
  дословно (замер: `SpRender('#include "frag"')` печатает `#include "frag"`) — резолвинг
  заявлен обязанностью хоста. Перед каждым рендером editor-core подставляет тексты из
  набора шаблонов (плоская папка, slug = имя файла; рекурсия с лимитом глубины и детектом
  циклов) — [ADR 0003](decisions/0003-include-resolution-and-template-set.md).
  **Подставляем по позициям, а не по именам:** `SpExtractDirectives` (движок ≥ `v0.2.0`)
  отдаёт каждое *вхождение* директивы со спаном, замена идёт с последнего к первому. Список
  слагов из `SpExtract` для этого не годится — он уникализирован, а значит закомментированный
  и живой `#include "frag"` в нём неразличимы; замер: развернуть оба и получить утечку текста
  и мусорного `#/` из комментария (комментарии не вложены — первый `#/` закрывает).
  Валидация при этом идёт по **неразвёрнутому** документу: позиции внутри подставленного
  текста показывать в редакторе некуда, — а включённые файлы валидируются отдельно, каждый
  в своих координатах (4.3).
- **Но разворачиваем не всё, что отдал движок.** Движок распознаёт `#include` **шире**
  эталона: `#includes "frag"`, `#include"frag"`, `#include "frag" junk`, `#include ""`,
  `#include "a" "b"` он считает инклюдом (и `SpValidate` ставит `include.unknown-target`), а
  `spintax-js`/PHP/Python рендерят это обычным текстом; обратно — `#include` + перевод
  строки + `"frag"` эталон видит, а движок нет. Это давний дефект движка (не из релиза
  позиций), корпусом не покрытый и запланированный к отдельной починке. Пока он есть,
  `ExpandIncludes` разворачивает вхождение, только если отданная движком строка (`Text`)
  укладывается в **эталонное** правило `^[ \t]*#include\s+"([^"]+)"\s*$`. Это не свой скан
  документа — это проверка формы уже найденной строки; когда движок сузится, фильтр станет
  no-op, а тесты, написанные по эталонному правилу, продолжат проходить. Обратный случай
  Studio тоже не развернёт — расхождение известное, оно в бэклоге.
- **Seed-режим**: фиксируешь сид (`TMulberry32Rng`) — предпросмотр стабилен,
  удобно сравнивать правки. Переключатель seed/random в верхней полосе.
- **locale** (верхняя полоса) уходит в `TSpContext.Locale` — влияет на плюрали
  (ru/uk/be, sr/hr/bs — 3 формы; остальное — 2).
- **Частичный предпросмотр**: если слева есть выделение — рендерится **только его
  текст, но в полном контексте документа**. Выделение может ссылаться на `%var%`,
  сидеть внутри `#def`/`#set`-области или зависеть от `#include` и `locale`,
  объявленных вне него; изолированный рендер тогда либо оставит `%var%` литералом,
  либо выдаст пустоту, и предпросмотр разойдётся с экспортом. Поэтому фрагмент
  рендерится так, будто он и есть шаблон, но с директивами документа
  (`#set`/`#def`) и рантайм-контекстом (locale + значения переменных)
  в области видимости. Механика: `SpRender(prelude + LF + fragment)`, где `prelude` —
  строки `#set`/`#def` документа в исходном порядке, `fragment = expand(текст выделения)`, а
  `expand` — резолвер `#include` (ADR 0003): инклюды разворачиваются первым шагом, потому
  что включённый текст тоже может нести `#set`. Прелюдию собираем из `SpExtractDirectives`
  (движок ≥ `v0.2.0`), а не своим сканом по строкам: движок разбирает директивы уже после
  вырезания комментариев (`ExtractDirectives(StripComments(…))`) и **делит** их по пяти
  терминаторам (LF, CR, CRLF, U+2028, U+2029). Замер: `#set %x% = A` внутри блочного
  `/# … #/` — не директива (рендер `[%x%]` даёт `%x%`), а наивный построчный скан утащил бы
  её в прелюдию и показал `A`.
  Две модели строк, и путать их нельзя: делятся директивы по пяти терминаторам, а
  `Line`/`Column` считаются по редакторским **трём** (LF, CR, CRLF). Замер: две директивы,
  разделённые U+2028, — это две директивы, но обе получают `Line = 1`, вторая
  `Column = 14`. Для нас это правильная сторона: SynEdit на U+2028 строку тоже не ломает,
  так что позиция ложится туда, куда смотрит пользователь.
  Оговорка: это не побайтовое совпадение с соответствующим куском полного рендера (свежий
  rng, отдельное разрешение `#def`) — это верный предпросмотр вывода самого фрагмента, а
  не гарантия тех же байтов.
- **Copy** — результат в буфер.
- Важно: `PostProcess := True` всегда для WYSIWYG (см. 7), иначе предпросмотр
  соврёт относительно боевых движков.

### 4.3 Валидация (нижняя вкладка «Диагностика»)

- `SpValidate(src, locale, knownIncludes, knownVariables)` на debounce после
  правок — движок даёт этот overload (`engine/src/Spintax.pas`), и передавать
  **оба** множества обязательно. `knownVariables` — имена, которые пользователь
  задал в панели переменных (4.4); без них валидатор выдаст `variable.undefined`
  на переменную, которую пользователь уже определил, и статус ложно покраснеет.
  Список `TSpDiag` (`code` + `severity` + позиции `Line`/`Column`/`EndLine`/`EndColumn`,
  см. 4.1). Вердикт: невалидно, если есть хоть один `error`.
- **Валидируется всё замыкание инклюдов, а не только открытый документ.** Развёрнутый текст
  не валидируем — позиции внутри подставленного текста некуда показывать, — поэтому каждый
  файл замыкания (сам документ плюс всё, что он тянет через `#include`) проходит
  `SpValidate` **отдельно, в своих координатах**, и диагностика группируется по файлу. Без
  этого документ зелёный, а экспорт деградирует из-за битой скобки или плюраля во фрагменте,
  и единственным следом остаётся флаг fullwidth-fallback без диагноза. В каждый проход уходят
  `knownVariables` = рантайм-переменные ∪ все имена `#set`/`#def` замыкания и `knownIncludes`
  = слаги всего набора: без этого объединения фрагмент, использующий макрос родителя, ловит
  ложный `variable.undefined` (замер — ADR 0003). Контракт `HealthReport` — M0, группировка в
  панели — M2.
- Индикатор в статус-строке: зелёный (valid) / красный (N ошибок) / жёлтый
  (только warning, напр. `variable.undefined`). Ошибка в любом файле замыкания красит статус
  красным — экспорт от неё пострадает так же, как от ошибки в самом документе.
- **Цена валидации нелинейна по числу директив** — замер движка: ~28 мс на 400 директивах,
  ~245 мс на 1600 в одном документе. Поэтому debounce здесь не косметика, а требование;
  замыкание валидируется с кэшем по файлу (ключ — текст файла, перевалидируется только
  правленый), и всё это живёт на engine-потоке (§5).
- **Собственные линты Studio** — то, чего движок не знает, помечены как наши, а не как его
  диагностика: сырой сентинел U+E000–U+E005 в документе (§7), цикл инклюдов, превышение
  лимита глубины разворота, коллизия слагов в наборе (§8), `#include`, который движок
  считает инклюдом, а эталон — обычным текстом (4.2).
- Клик по строке диагностики — **прыжок кареткой в `Line:Column`** из `TSpDiag`
  (и выделение диапазона, если есть `End*`). При `Line = 0` (позиция неизвестна) строка
  диагностики остаётся в панели, но никуда не прыгает — Studio не выдумывает место.
- Коды: скобки, `set/def.malformed`, `definition.duplicate-name`,
  `def.include-in-value`, `permutation.unknown-key`,
  `permutation.min/maxsize-not-integer`, `plural.nested-brackets`,
  `plural.arity`, `plural.count-macro`, `variable.self-reference`,
  `variable.circular-reference`, `variable.undefined`, `include.unknown-target`.
- `knownIncludes` — слаги набора шаблонов (плоская папка, §8 и ADR 0003; сравнение без
  учёта регистра — именно так его делает сам движок, замер в ADR), `knownVariables` —
  рантайм-контекст пользователя, объединённый с именами `#set`/`#def` всего замыкания
  (см. выше). Оба множества одинаковы для всех проходов замыкания.

### 4.4 Панель переменных (нижняя вкладка «Переменные»)

- `SpExtract(src)` → `refs / sets / defs / includes`. Важно: `SpExtract` отдаёт **только
  имена** — значений `#set`/`#def` в нём нет. Значения (и позиции для «прыгнуть к
  определению») берём из `SpExtractDirectives` (§4.2) — это те же директивы, которые видит
  рендер, так что панель и предпросмотр не разъедутся. Дерево:
  - определённые (`#set`/`#def`) с их значениями;
  - ссылки `%var%` без определения → помечены (рантайм-переменные), тут же поле
    задать значение для предпросмотра;
  - `#include`-цели, с пометкой известна/нет.
- Правка значения рантайм-переменной мгновенно меняет предпросмотр.

### 4.5 LLM-петля: автор → проверка → починка

Третий режим поверх «редактируешь сам»: модель пишет, движок проверяет.

- **Generate**: бриф пользователя («спинтакс про X для ниши Y, вот переменные»)
  + канонический **authoring-prompt** (PROMPT_VERSION 2) как system → модель
  возвращает шаблон в левую панель.
- **Verify**: возвращённый шаблон сразу через `SpValidate` + N пробных
  `SpRender` (детект пустых рендеров и fullwidth-fallback как признака битого
  плюраля).
- **Fix / repair loop**: если есть `error`-диагностика — она формализованно уходит
  обратно модели, и `Line`/`Column` берутся **из `TSpDiag`**, а не угадываются
  («строка 3, кол. 1: `plural.arity`, ru требует 3 формы»). Точная координата плюс
  фрагмент этой строки резко повышают шанс, что модель починит нужное место; при
  `Line = 0` даём код без координаты. Модель чинит, цикл до чистого вердикта или до
  лимита итераций. Человек включается, когда валидно.
- **Провайдеры** (абстракция `TLlmProvider`): облачные (Anthropic, OpenAI,
  Google) + локальная модель через localhost (Ollama/совместимый OpenAI API).
  authoring-prompt провайдер-независим. Ключи — локально, в Credential Manager (§6).
  Ещё один **возможный** адаптер за тем же интерфейсом — **управляемый провайдер** (наш
  прокси на Cloudflare): upstream-ключ на сервере, клиент шлёт запрос со своим
  service-токеном. Это путь монетизации для тех, у кого своего ключа нет; решение пока не
  принято, следствия — в §10/§11. BYOK и локальная модель остаются дефолтом.
- Синонимы (4.1) могут ходить в тот же слой.

### 4.6 Пакетная генерация и экспорт (нижняя вкладка «Варианты / Экспорт»)

- **Generate N**: `SpRender` × N с воспроизводимыми сидами. Деривация фиксирована:
  `seed_i = seedBase + i` (`i = 0..N-1`). `TMulberry32Rng` перемешивает сид
  внутри (add-constant + xorshift-multiply), поэтому последовательные сиды дают
  раскоррелированные потоки — усложнять деривацию не нужно. `seedBase` — из поля
  или случайный, но **записывается**, чтобы весь набор воспроизводился.
- **Воспроизводимость экспорта**: колонка сида всегда доступна (в `.xlsx` — колонка,
  в `.txt` — опциональный префикс), чтобы любой вариант можно было перегенерировать
  как `SpRender(tmpl, ctx{seed})`. Воспроизводимость требует того же движка (тег) и
  того же контекста (locale + значения переменных) — экспорт при желании пишет и их.
- **Уникальность/шинглы**: дедупликация по шингловой близости (порог и размер
  шингла задаются) — как на spintax.ru. Дедуп имеет **бюджет ретраев**: на выброшенный
  дубль берётся следующий сид (`seedBase + N`, `+N+1`, …) до добора N уникальных или
  до исчерпания бюджета. Итог — отчёт **requested / generated / dropped**, чтобы было
  видно, добрал ли набор до N и какой ценой (низкая вариативность шаблона всплывает
  именно здесь).
- **Экспорт**: `.xlsx` (колонка вариантов + колонка сида), `.txt` (по строке,
  опционально с сидом), «каждый текст — отдельный файл».

## 5. Архитектура

Слои, снизу вверх:

1. **Движок** — `spintax-win` (`unit Spintax`), встроен в процесс как git
   submodule на теге (ADR 0001, `docs/decisions/`). Не трогаем. API: `SpRender`,
   `SpNeutralize`, `SpSafetyRestore`, `SpStripSentinels`, `SpExtract`, `SpValidate`
   (overload с `knownVariables`; `TSpDiag` несёт позиции `Line`/`Column`/`EndLine`/
   `EndColumn` с ≥ `v0.2.0`), `NormalizeBaseLang`, `PluralArity`. RNG-шов:
   `TFirstRng`, `TLastRng`, `TSequenceRng`, `TMulberry32Rng`.
2. **editor-core** (`SpxStudio.pas`) — тонкий, чистый, zero-dep слой оркестрации
   над движком, GUI- и сеть-независимый. Именно к нему одинаково цепляются GUI и
   LLM-петля. Весь Studio-контекст (locale, значения рантайм-переменных, известные
   инклюды и имена рантайм-переменных) течёт через этот слой в движок — граница
   между «контекстом документа» и чистым API движка живёт здесь. Функции (набросок):
   - `ExpandIncludes(tmpl; set): string` — подстановка `#include` из набора шаблонов
     (ADR 0003) по спанам от `SpExtractDirectives`, с последнего вхождения к первому,
     рекурсивно, с лимитом глубины и детектом циклов. Идёт перед каждым рендером и **не**
     идёт перед валидацией. `set` — карта `slug → text` в памяти: на диск editor-core не
     ходит, папку читает хост, поэтому M0 проверяется без файловой системы.
   - `RenderSample(tmpl; ctx): string` — один пример (`ctx` несёт `Vars` + `Locale`
     + `PostProcess := True` + rng).
   - `RenderFragment(doc; sel; ctx): string` — выделение в контексте документа (4.2):
     прелюдия директив от движка плюс сам фрагмент.
   - `RenderBatch(tmpl; ctx; n; seedBase): TStringList` — N вариантов, `seed_i =
     seedBase + i` (см. 4.6).
   - `ExtractModel(tmpl): TVarModel` — переменные/инклюды для панели.
   - `HealthReport(doc; ctx; set): TReport` — диагностика по всему замыканию инклюдов:
     `SpValidate` отдельно на каждый файл (документ плюс всё включённое), каждый в своих
     координатах, с кэшем по тексту файла — на правку перевалидируется только тот файл,
     который правят (4.3: цена растёт нелинейно по числу директив). `knownIncludes` = слаги набора, `knownVariables` = рантайм-переменные ∪
     имена `#set`/`#def` всего замыкания — передавать **оба** множества обязательно, иначе
     заданная в панели переменная или макрос родителя ловят ложный `variable.undefined`
     (4.3). `TReport` прокидывает позиции `TSpDiag` без изменений и помнит, из какого файла
     диагноз, — это потребляют squiggles, прыжок и repair-петля. Плюс M пробных рендеров
     **развёрнутого** текста в контексте `ctx` и флаги (есть пустые? есть
     fullwidth-fallback? сколько вариативности?). Это то, что потребляет и панель, и
     repair-петля.
3. **LLM-слой** (`SpxLlm.pas`) — `TLlmProvider` + адаптеры + `TAuthoringLoop`
   (Generate/Verify/Fix). HTTPS-клиент, стриминг, хранение ключей локально.
4. **GUI** — окно, панели, редактор с подсветкой, горячие клавиши.

Поток данных: правка в редакторе → debounce → editor-core `HealthReport` +
`RenderSample` → обновляются правая панель, диагностика, переменные. Кнопки
Generate/Fix → LLM-слой → left panel → тот же цикл проверки.

**Один engine-поток.** В движке есть ленивый глобал — `GAbbrevs`, список аббревиатур
post-process (`src/Spintax.pas`), — и инициализируется он без синхронизации: два *первых*
рендера из разных потоков дают гонку. Плюс post-process заметен на больших текстах (замер
движка после линеаризации: 0.7 с на 237 КБ), а живой предпросмотр дёргает его на каждый
debounce. Правило Studio: на старте один холостой рендер прогревает глобал, дальше **все**
вызовы движка идут на одном выделенном engine-потоке по схеме «побеждает последний» (новая
правка отменяет ещё не отданный результат), а UI-поток движок не вызывает никогда. После
прогрева глобал только читается, так что пакетную генерацию (4.6) при желании можно
распараллелить. Закладывать это надо сразу: ретрофит потока в готовый UI дороже.

## 6. Технологический стек

- **GUI-фреймворк: Lazarus / LCL** — решено, см. [ADR 0002](decisions/0002-gui-lazarus-lcl.md).
  Тот же FPC, которым собран движок; бесплатно; нативные Win-виджеты; один
  самодостаточный .exe; всё остаётся MIT. Delphi VCL был возможной альтернативой
  (движок компилится под UTF-16 Delphi), но это лицензия и вес, а Starter не тянет
  коммерческий продукт.
- **Редактор с подсветкой**: SynEdit (есть и в Lazarus, и в Delphi) —
  кастомный highlighter под spintax-грамматику.
- **HTTP к моделям**: `fphttpclient`/`opsslsocket` или Synapse; стриминг ответа.
- **xlsx-экспорт**: FPSpreadsheet (Lazarus) либо простой OpenXML-writer.
- **Хранение**: локальный конфиг (INI/JSON) в `%APPDATA%`.
- **Секреты — только Windows Credential Manager (DPAPI-backed), НИКОГДА не плейнтекст в
  конфиге.** Это касается двух разных секретов, и путать их нельзя:
  - **BYOK-ключ** провайдера (Anthropic/OpenAI/Google) — ключ самого пользователя, уходит
    напрямую к его провайдеру;
  - **токен нашего управляемого сервиса** (если появится платный tier, §10/§11) — это НЕ
    AI-ключ: upstream-ключ живёт на сервере, у клиента только токен доступа к нашему сервису.
  Оба — в Credential Manager, оба локальные, оба переживают BYOK-принцип. В `%APPDATA%`
  и рядом с `.exe` (§7) секретов нет.

## 7. Технические требования и подводные камни

- **Кодировка (обязательно).** FPC-хост один раз на старте: `DefaultSystemCodePage
  := CP_UTF8;` — иначе кириллица молча превращается в `'?'` ещё до движка.
  Библиотека это за хост не сделает.
- **PostProcess по умолчанию False.** `Default(TSpContext)` оставляет
  `PostProcess = False` (в JS-референсе дефолт `true`). Для WYSIWYG-предпросмотра
  Studio **всегда** ставит `True` явно, иначе косметика не применится и правая
  панель разойдётся с боевым выводом.
- **RNG-режимы.** Предпросмотр — `TMulberry32Rng` (seed) или свежий инстанс на
  reroll; пакет — разные сиды на вариант; `TFirstRng`/`TLastRng` не для UI, они
  для детерминированных проверок.
- **`#include` резолвит хост.** Движок печатает директиву дословно — это его заявленное
  поведение, а не пробел. Резолвер живёт в Studio (ADR 0003), движок для этого трогать не
  надо; от движка нужны только **позиции вхождений**, а не список слагов.
- **Редакторская сторона и рендер по-разному видят сырые сентинелы.** `SpExtract`,
  `SpValidate` и `SpExtractDirectives` читают исходник как написано, а `SpRender` удаляет
  зарезервированные U+E000–U+E005 **до** разбора. На документе с сырыми PUA-символами
  прелюдия, панель переменных и разворот инклюдов расходятся с тем, что реально
  отрендерится, причём в обе стороны: сентинел внутри `#set` прячет директиву от панели, но
  не от рендера, а сентинел внутри `/#` наоборот. Это контракт семьи, а не дефект порта — у
  эталона `extract`/`validate` расходятся с `render` ровно так же. Практика: чужой текст
  входит в шаблон только через `SpNeutralize`, а сырой U+E000–U+E005 в документе Studio
  показывает линтом (4.3).
- **Комментарии не вложены.** `/# a /# b #/ c #/ d` → `C #/ d`: первый `#/` закрывает блок.
  Поэтому любая подстановка текста внутрь комментария (например, разворот
  закомментированного `#include` фрагментом, у которого есть свой комментарий) выпускает
  наружу и текст, и мусорный `#/`.
- **Ленивый глобал в движке.** `GAbbrevs` строится при первом post-process без
  синхронизации → прогреть холостым рендером на старте и держать вызовы движка на одном
  потоке (§5).
- **Движок чистый.** Никакой сети/GUI в движок не добавляем — это его заявленное
  свойство. Всё новое — в слоях 2–4. Исключение — чистые текстовые примитивы, которых
  хосту не из чего собрать: так в `v0.2.0` уезжает `SpExtractDirectives` (§4.2), как до
  этого уехали позиции `TSpDiag`.
- **Корпус не вендорить.** Если Studio держит свои тесты — на общий golden-корпус
  ссылаться, а не копировать (решение `0001` в движке).
- **Хранилище — через known-folder API, не рядом с .exe.** Настройки/шаблоны/ключи пишем
  в профиль пользователя (`SHGetKnownFolderPath` / `%APPDATA%`, `LocalAppData`), а не в
  папку приложения. Это обязательно для MSIX-контейнера (запись рядом с .exe там
  виртуализируется/запрещена) и заодно снимает требование admin-прав (§11).

## 8. Модель состояния (набросок)

- **Document**: текст шаблона, путь файла, локаль, рантайм-контекст
  (`name → value`), режим rng (seed/random) и текущий сид.
- **Workspace/набор**: плоская папка с `*.spintax` рядом с текущим документом; slug —
  имя файла без расширения, сравнение без учёта регистра. Хост читает папку и отдаёт в
  editor-core карту `slug → text`; слаги питают `knownIncludes` для валидации и служат
  таблицей подстановки для резолвера `#include`
  ([ADR 0003](decisions/0003-include-resolution-and-template-set.md)). Два файла, слаги
  которых различаются только регистром (на NTFS невозможно, но приезжает архивом или
  клоном с чувствительной ФС), — **ошибка набора**: слаг не резолвится, и набор говорит
  почему, вместо «какой файл первым попался». У несохранённого документа набора нет:
  инклюды остаются дословными, и панель переменных это показывает.
- **Settings**: провайдеры и ключи, дефолтная локаль, пороги дедупликации,
  горячие клавиши.
- **Session**: история LLM-диалога петли, последние сгенерированные варианты.
  Дефолт — **не персистить**; предлагать ли opt-in сохранение между сессиями —
  открытый вопрос уровня M4 (§10, отражён в `docs/TODO.md`). Здесь описан только
  дефолт, само решение ещё не принято.

## 9. Этапы и релизы

- **Pre-M0 — выпустить движок `v0.2.0` и сдвинуть submodule.** Оба дополнения публичного
  API уже лежат в `main` движка и едут в этот тег: позиции `TSpDiag` (§4.1) и
  `SpExtractDirectives` (§4.2) — список директив `#set`/`#def`/`#include` со спанами в
  координатах исходника, текстом строки и значением
  макроса. Нужны оба: `HealthReport` обязан прокидывать позиции, а резолвер инклюдов,
  прелюдия фрагмента и значения в панели переменных — все три — должны брать директивы у
  движка, а не сканировать документ самостоятельно. Как только тег есть — сразу сдвинуть
  submodule (`engine/`), **не ждать M2**, иначе M0 начнут писать на API, которого в пине
  (`v0.1.0`) нет.
- **M0 — editor-core.** `SpxStudio.pas` над движком: `ExpandIncludes`, `RenderSample`,
  `RenderFragment`, `RenderBatch`, `ExtractModel`, `HealthReport`. Чистый Pascal, покрыт
  тестами. Верифицируемо без GUI.
- **M1 — GUI-оболочка.** Две панели, SynEdit + spintax-highlighter, живой
  предпросмотр, парные скобки, статус валидности. DeepL-скелет.
- **M2 — панели.** Переменные (SpExtract), диагностика (SpValidate) со squiggles и
  прыжком к ошибке **по позициям `TSpDiag`** (не свой скан; требует движок ≥ `v0.2.0`),
  частичный предпросмотр, select-and-wrap, горячие клавиши.
- **M3 — экспорт.** Generate N, дедуп по шинглам, xlsx/txt/по-файлу.
- **M4 — LLM-петля.** `TLlmProvider` + адаптеры + `TAuthoringLoop`
  (Generate/Verify/Fix), authoring-prompt как system, локальная модель. Синонимы.

M0 переиспользуется целиком; GUI и LLM независимы, порядок M3/M4 взаимозаменяем.

### Релизы

- **R0 — первый Store-релиз = M0–M3, offline-only.** Редактор, валидация, предпросмотр,
  переменные, экспорт — и **ничего от AI**: нет LLM-UI (кнопки Generate/Fix скрыты), нет
  настроек провайдеров, нет управляемого AI, нет покупок/paywall/trial. Это сознательный
  scope: без генеративного AI первая подача **вообще не попадает** под Store-политику Live
  Generative AI (disclosure/report, §11), а офлайн-база и так есть — рецензент проверяет весь
  R0 без ключа и сети.
- **R1+ — AI.** M4 (LLM-петля, BYOK + локальная модель) включает генеративный AI → с этого
  релиза начинают действовать AI-disclosure/report и privacy для BYOK (§11).
- **R2+ (опционально) — управляемый AI-tier** (монетизация, §10/§11): отдельное коммерческое
  решение, свой ADR, после R1.

Layout §3 (кнопки `[Generate] [Fix]`, вкладки провайдеров) — это целевой вид **R1+**; в R0
эти элементы не показываются.

## 10. Вопросы

### Решено (2026-07-23, дополнено 2026-07-25)

- **Резолвинг `#include` и формат набора шаблонов** (2026-07-25): разворачивает Studio по
  **позициям вхождений** от движка, набор — плоская папка с `*.spintax`, slug = имя файла —
  [ADR 0003](decisions/0003-include-resolution-and-template-set.md). Движок инклюды не
  резолвит и печатает директиву дословно; это его заявленное поведение (замеры — в ADR).
- **Имя и репозиторий:** `spintax-studio`, отдельный от движка. Создан.
- **Как тянем движок:** git submodule на `engine/`, пин на тег (`v0.1.0`) —
  [ADR 0001](decisions/0001-engine-as-submodule.md).
- **Lazarus/LCL против Delphi VCL:** Lazarus/LCL —
  [ADR 0002](decisions/0002-gui-lazarus-lcl.md).

### Ещё открыто (уровень M3/M4, не гейтят M0/M1)

- Тезаурус для синонимов: локальная база (какая?) или только LLM.
- Персистить ли историю LLM-петли и наборы вариантов между сессиями.
- **Тип аккаунта в Partner Center — individual или company** (§11). Решить **до первой
  подачи**: между ними потом нормально не переключиться. Для коммерческой публикации —
  company. Это бизнес-решение пользователя, не код.
- **Управляемый AI-провайдер как монетизация (прокси на Cloudflare) — рассмотреть, не
  решено.** Технически ложится чисто: ещё один адаптер за `TLlmProvider` (§4.5),
  upstream-ключ на Worker, у клиента — service-токен (§6). Дефолт (BYOK + локальная модель)
  и офлайн-база не меняются, значит Store-ревью-ключ (§11) сохраняется. **Но цена не
  нулевая:**
  - **меняется поток данных.** BYOK/локально — промпты нашей инфраструктуры не касаются
    вообще; управляемый tier — промпты идут транзитом через наш Worker, то есть мы
    становимся data processor. Чтобы удержать этику — прокси **pass-through, без логирования
    промптов** (zero-retention), но это всё равно транзит, и privacy policy это должна
    отражать;
  - **растёт вес Store-policy** (§11): при BYOK мы лишь *способствуем* AI, а при своём
    сервисе — *оперируем* генеративным AI напрямую → disclosure и канал жалоб становятся
    строже, ответственность за вывод — больше наша;
  - **нужна инфраструктура сверх «маленького сервера»:** биллинг (Cloudflare не биллит —
    Stripe/аналог), метеринг кредитов/подписки, rate-limit и обработка abuse.
  Вывод: путь реальный и архитектурно дешёвый, но это отдельный **платный tier поверх
  бесплатного BYOK-продукта**, а не замена ему; браться — после M4, отдельным решением.

## 11. Дистрибуция и Microsoft Store

Store принимает обычные **Win32-приложения**, не только UWP, поэтому Lazarus/LCL — не
блокер. Главный риск не технический, а **policy вокруг AI/контента** (см. ниже).

### Целевой путь упаковки

- **Основной — MSIX.** Обёртка вокруг того же `.exe` (§1). Store сам хостит пакет,
  управляет обновлениями и **пере-подписывает** пакет для доставки — своей инфраструктуры
  подписи/хостинга/апдейтов не нужно. Это целевой publish target.
- **Запасной — EXE/MSI installer.** Store принимает и его, но тогда: нужен versioned
  **HTTPS-URL** к инсталлеру, инсталлер обязан уметь **silent install**, а подпись,
  хостинг и механика обновлений — **на нас**. Берём только если MSIX почему-то не подойдёт.

### App identity (заложить с самого начала)

- Стабильное **имя пакета** и **publisher** (должны совпасть с Partner Center), не менять
  после первой подачи.
- **4-частная версия** `Major.Minor.Build.Revision` в манифесте MSIX, монотонно растёт на
  каждую подачу. Маппится на версию приложения и тег движка, против которого собрано
  (submodule ≥ `v0.2.0` для позиций диагностики, §4.1).
- **Набор иконок/ассетов** под Store и плитки (несколько размеров, Store-logo) — дизайн-задача.

### No admin

Обычная работа **не требует прав администратора** — ни установка через Store, ни запуск, ни
запись настроек. Прямое следствие принципа «один .exe» и хранилища через known-folders (§7).

### Store-policy вокруг AI — ключевое

**Пока** у нас **BYOK**: пользователь приносит свой ключ (Anthropic/OpenAI/Google) или
локальную модель; **мы не оперируем AI-сервисом и не хостим контент**. Это резко сужает
policy-поверхность, но **не снимает** обязанностей, если в продукте есть live generative AI.
Если добавим управляемый провайдер (платный tier, §10), эта рамка **меняется**: мы начинаем
*оперировать* AI и становимся транзитом данных → всё ниже становится строже, а privacy
policy обязана описать zero-retention-прокси. Обязанности при BYOK:

- **AI disclosure.** Раскрыть наличие генеративного AI в metadata листинга и в Partner
  Center.
- **Report inappropriate content.** Дать пользователю способ сообщить о проблемном
  AI-выводе. У локального BYOK-инструмента нет общей ленты — значит это контакт/ссылка для
  репорта (в приложении и в листинге), а не серверная модерация.
- **Privacy policy — фактически обязательна** при наличии LLM/ключей/сети: что генерируется
  пользователем, куда уходят данные (BYOK — напрямую к его провайдеру, мы не в потоке;
  управляемый tier — транзитом через наш zero-retention-прокси, без хранения промптов),
  как хранятся секреты (только Credential Manager/DPAPI, §6), что телеметрии нет.

### Прохождение ревью

- **Офлайн-база — стратегия (§1).** Рецензент открывает приложение и проверяет
  редактор/валидацию/рендер/экспорт **без ключа и сети**; AI — opt-in. Никаких «плясок»,
  чтобы увидеть, что продукт работает.
- **Листинг — продукт, а не dev-tool-заглушка.** Внятные скриншоты и описание понятного
  сценария (шаблон → предпросмотр → экспорт), не голый редактор.

### Коммерция

- **R0 — без покупок:** ни paywall, ни trial, ни IAP. Бесплатное офлайн-приложение, и
  первая подача не тащит за собой ещё и financial-policy.
- **Платный управляемый AI-tier (R2+, §10) — отдельный ADR перед реализацией.** Microsoft
  для non-game PC-приложений допускает и **Microsoft Store IAP**, и **secure third-party
  purchase API** (Stripe/аналог) для цифровых услуг, но выбор надо раскрыть в Partner Center
  и в UX. ADR должен зафиксировать: механизм оплаты (Store IAP vs third-party), цены/условия,
  отмену/возврат, disclosure в Partner Center, и тип аккаунта (company). Не начинать биллинг
  до этого решения.

### Аккаунт

Открывается через **Partner Center**. **individual vs company** решить до первой подачи —
переключение между ними внутри аккаунта потом нормально не работает; для коммерции — company
(§10). Условия/сборы — по текущей документации Microsoft (ссылки ниже).
